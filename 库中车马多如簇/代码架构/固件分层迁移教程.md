# 固件工程分层迁移教程

[←MOC](MOC.md)

> 用途：将已有 MCU 固件工程按目标目录中的 MOC 进行文件归类，并同步工程内部路径。本文可直接交给 AI 作为执行规范。

本教程适用于裸机或使用 FreeRTOS 等 RTOS 的工程，也适用于不同芯片、外设组合、中间件和 IDE。**文件名、文件数量、目录深度和需要检查的字段都由实际工程决定；示例不是固定清单。**

## 1. 任务范围与原则

迁移目标是：文件放入正确的分层目录，工程仍引用同一批有效源文件、头文件、库和启动配置。

- **MOC 是只读的分类依据。不得修改、覆盖、重命名任何 MOC.md，也不要将其中示例名称替换成实际工程名。**
- 保留原工程名称、芯片型号和文件名。本文的 `project`、`<芯片系列>` 等均为占位符，执行时使用实际值。
- 区分文件移动和入口集成。仅要求整理目录时保持运行逻辑；用户要求接入框架时，按第 7 节把 main_frame.c 中的必要逻辑合入 CubeMX 生成的 main.c，不替换硬件入口，也不增加第二个 main()。
- 对已有源码优先只移动文件，通过修正工程引用和搜索目录维持构建。只有确实存在失效的相对引用时，才修改相应源码引用。
- 遇到同名目标文件，先比较内容和用途；不得覆盖现有实现，也不得通过删除一份文件来掩盖入口冲突。
- 保留第三方组件内部目录、许可证及必要依赖，不因为暂未引用就裁剪第三方包。
- 实际存在的文件才需要归类；MOC 中的示例目录、链接脚本和组件不代表必须创建对应文件。
- 先识别原工程的运行方式。裸机保持裸机，RTOS 保持原任务、同步机制和调度器流程；目录迁移不能将二者相互转换。
- 不预设外设名单、RTOS 实现、内存分配方案、源文件数或搜索目录数。未列举的文件同样需要按内容、依赖和实际构建角色判断。
- 第三方源码、工程生成的适配代码、业务代码和配置文件可能混在同一原目录；不能仅凭原目录名整包归入同一层。
- Keil 的 Manage Project Items / Project 树分组也属于迁移范围。物理目录、工程文件引用和 Group 归属必须一致，不能只修正磁盘路径而沿用旧的默认分组。
- 有 OS 时采用用户指定的 OS 架构：`07_os` 存放操作系统源码，`04_platform/platform_os` 存放 OSAL，业务任务归 App，业务服务归 Service。即使原始 CubeMX 把内核放在 Middlewares 中，也按职责迁入 `07_os`。

## 2. 明确路径基准

执行前识别三个目录：

| 代号                      | 含义                              | 示例                                                               |
| ------------------------- | --------------------------------- | ------------------------------------------------------------------ |
| SOURCE_ROOT               | 待迁移的原始工程目录              | 某个 CubeMX 工程目录                                               |
| TARGET_ROOT               | 已包含各层目录和 MOC 的固件根目录 | `03_Firmware/`                                                   |
| PROJECT_DIR               | 某个迁移后工程文件所在目录        | `TARGET_ROOT/10_toolchain/<实际工具链目录>/`                     |
| OS_REFERENCE_ROOT（可选） | 用户指定的 OS 架构参考目录        | 含 `07_os/` 和 `04_platform/platform_os/` 的参考 firmware 目录 |

下文目标路径均相对于 TARGET_ROOT。工程内部的相对路径必须按对应工具的解析基准计算，不能按工作区根目录猜测。

多个 IDE、构建目标或固件镜像应分别记录解析基准、条件编译和输入清单；构建脚本的工作目录不一定等于脚本所在目录。

通用计算方法：

```text
旧引用绝对路径 = 解析(旧引用所属配置的原解析基准 + 旧相对路径)
目标文件绝对路径 = 查询迁移映射表(旧引用绝对路径)
新相对路径 = relative(引用所属配置的新解析基准, 目标文件绝对路径)
```

Windows 工具可能使用反斜杠，XML 也可能使用正斜杠。按原配置支持的格式写回。

## 3. 迁移前检查

1. 阅读目标根 MOC 和相关子目录 MOC，确定每层职责；全过程保持 MOC 原样。
2. 列出原工程全部文件，包括隐藏配置，例如 `.mxproject`。区分源码、配置、第三方文件、调试设置和编译产物。
3. 读取工程的所有构建目标，提取源文件清单、IncludePath、库路径、启动文件、链接脚本和构建前后命令。
4. 检查原工程和目标模板中的 `main()`、中断入口及 HAL 回调，确定当前实际参与构建的实现。
5. 建立逐文件迁移映射表，检查目标重名、共享依赖和目标目录以外的引用。
6. 保存待修改配置的原内容，记录只移动文件的哈希值；后续仅撤回本任务引入的变更，保留用户已有修改。

同时识别实际启用的外设、中间件、RTOS 与接口封装，以及每个目标使用的编译器、CPU/FPU/ABI、宏定义和文件排除设置。信息应由实际源码、生成配置与构建配置交叉确认；文件存在不代表参与构建。

若目标目录的 MOC 描述裸机架构而原工程使用 RTOS，先检查用户是否指定 OS_REFERENCE_ROOT：已指定时，读取参考目录的根 MOC、07_os、Platform OS、App 初始化和 Config 说明，将其作为 OS 部分的分类依据；不修改两处 MOC，也不把 OS 放回普通 vendor 目录来绕过分层。未指定且无法确定兼容布局时，先保留相关文件并说明架构差异，不删除 RTOS 或改写成裸机。读取参考目录不代表要复制全部框架实现；OSAL 接入、任务重构和功能移植须与单纯目录迁移区分。

映射表建议字段：

```text
原绝对路径 | 新绝对路径 | 所属层 | 文件角色 | 所属构建目标 | 操作类型 | 归类理由
```

## 4. 按 MOC 分配文件

| 层或目标位置           | 应放入的内容                                                                     | 分类注意事项                                                             |
| ---------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `08_core/Core/Src/main_frame.c`（原框架 main.c） | 框架入口参考，保存应用初始化及主循环接入逻辑 | 保留为独立参考文件；若其中仍定义 main()，排除编译。实际入口使用 CubeMX 生成的 main.c。 |
| `01_app/`            | 实际存在的应用控制、业务任务、消息处理、状态机、应用回调转发                     | 是否使用状态转移表或事件队列以原工程为准，不把芯片中断向量文件混入本层。 |
| `02_service/`        | 按业务功能组织、由状态转移动作调用的服务                                         | 只迁移实际服务实现，不凭目录名生成空业务。                               |
| `03_config/`         | 板级、功能、项目和版本配置                                                       | 实际文件位置以本层 MOC 为准。                                            |
| `03_config/cubemx/`  | 原名 `.ioc` 文件、`.mxproject`                                               | 保留实际工程文件名；文件移动不代表 CubeMX 已支持分层生成。               |
| `04_platform/`       | Adapter、Wrapper、MCU Port 及其实现                                              | CubeMX 生成的外设初始化文件不能仅因涉及 GPIO/SPI 就当作 Port。           |
| `05_bsp/`            | 具体设备的 Handler、Driver                                                       | 自研设备驱动与芯片厂商 HAL 分开，依照 MOC 的依赖方向归类。               |
| `06_middlewares/`    | 通用算法、协议栈、文件系统、图形库和非 OS 的第三方组件                           | 厂商附带组件按 MOC 放入 `vendor/`；OS 内核及配套端口归 `07_os`。     |
| `07_os/`（有 OS 时） | 操作系统内核、配套头文件、内核 portable 端口、内存管理实现及随 OS 使用的接口封装 | 不放业务任务和 OSAL Wrapper；按下节 OS 布局处理。                        |
| `08_core/Core/`      | 生成的系统、外设、中断头文件及实现、硬件 main.c、MSP、system 文件                | MOC 指定保留 Core 布局时，不额外拆分生成文件。                           |
| `08_core/`           | 对应芯片和工具链的启动文件                                                       | 启动文件原来位于 IDE 目录时也按职责迁入；保留汇编内容。                  |
| `09_drivers/`        | CMSIS、芯片 HAL/LL 和底层厂商依赖                                                | 保留厂商目录结构；HAL 配置头文件的位置以 MOC 为准。                      |
| `10_toolchain/`      | IDE 工程、工具链包、链接脚本、构建脚本、调试配置                                 | Keil 工程通常保留在 `MDK-ARM/`；其他 IDE 按原工程实际组织。            |

常见 CubeMX 工程的映射示例，仅在对应目录存在且职责一致时使用：

```text
原工程/Core/                       -> 按角色归入 Core、App、Config 等目标层
原工程/Drivers/                    -> 09_drivers/
原工程/Middlewares/非OS组件         -> 06_middlewares/ 对应子层
原工程/Middlewares/实际OS组件       -> 07_os/，保留组件内必要目录结构
原工程/MDK-ARM/startup_<芯片>.s     -> 08_core/startup_<芯片>.s
原工程/MDK-ARM/工程配置与调试文件   -> 10_toolchain/MDK-ARM/
原工程/<原工程名>.ioc              -> 03_config/cubemx/<原工程名>.ioc
原工程/.mxproject                  -> 03_config/cubemx/.mxproject
```

如果 MOC 将 `stm32<系列>xx_hal_conf.h` 单独放在 `09_drivers/`，将其从 Core 头文件目录迁出，并补充对应搜索目录。不得同时留下两个可能被不同构建目标选中的配置副本。

### 4.1 外设不同：按职责识别，不按固定文件名匹配

- 从实际工程识别外设初始化代码、IRQ、DMA、MSP 以及芯片厂商驱动依赖；不要要求每个工程必须具有某几个外设文件。
- 外设初始化可能集中在 main.c，也可能独立为多个 C/H 文件。保留原生成粒度，不为满足目录示例而拆函数或新建文件。
- 通用规则是：芯片生成的初始化和中断代码归 Core；厂商 HAL/LL 归芯片驱动层；自研 MCU Port 归 Platform；具体外部器件的 Handler/Driver 归 BSP。
- 同一外设可以有多个实例和多个中断源。保留全部句柄、初始化顺序、DMA/IRQ 绑定、回调和编译条件，不根据文件数量推断实例数。
- 不同芯片可能有多个核、启动文件或固件镜像。分别保留原目标的启动链、系统实现和链接布局，不把合法的多镜像结构当作重复文件删除。

### 4.2 使用 FreeRTOS 或其他 RTOS 时

以下是职责示例。实际名称、版本、封装形式和目录结构应从工程识别，不要求这些文件全部存在。

| 文件或组件角色                         | 归档原则                                                                                                                 | 必须保留和同步的内容                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| RTOS 内核与第三方附带文件              | 归入 `07_os/`，按实际组件保留内部结构                                                                                  | 内核源文件、头文件、许可证和原版本。                                   |
| 内核 portable 端口                     | 跟随内核组件归档；项目自研的 OS 适配层再按 MOC 判断                                                                      | 原先启用的 CPU、编译器和端口变体；不能把所有候选端口加入构建。         |
| RTOS 内存管理实现                      | 保留原构建目标的选择及位置映射                                                                                           | 实际使用的 heap 实现或自定义分配器，不擅自替换或将互斥实现全部编译。   |
| CMSIS-RTOS、CMSIS-RTOS2 等接口封装     | 随实际 RTOS 软件包归入 `07_os/`，不与 `09_drivers/CMSIS` 的内核设备支持混淆                                          | 封装实现、接口头文件、版本、搜索路径及原依赖。                         |
| 内核配置，例如 FreeRTOSConfig.h        | 归到 `07_os/` 内该 RTOS 的配置位置，具体子目录按实际组织；参考明确另有位置时遵从其规定                                 | 保留原文件名和宏，确保构建使用正确配置；不把它重命名为 rtos_config.h。 |
| 应用 RTOS 资源参数，例如 rtos_config.h | `03_config/`                                                                                                           | 工程级任务、队列及同步资源参数；与内核配置、OSAL 选择配置区分。        |
| 生成的 RTOS 初始化和任务创建代码       | 应用初始化和资源创建职责归 `01_app/app_init/`；混有硬件初始化的文件先保留在 `08_core/Core/`，未经功能重构不拆源码    | 原初始化入口、默认任务、同步对象、用户代码区和任务创建顺序。           |
| 自研业务任务与资源表                   | 任务归 `01_app/` 相应模块，资源创建/句柄管理按参考归 `01_app/app_init/user_task_config/`；业务服务归 `02_service/` | 任务入口、资源配置表、优先级、栈参数和同步逻辑原样保留。               |
| OSAL 公开头文件                        | `04_platform/platform_os/inc/`                                                                                         | 统一接口、类型、错误码、配置及各资源 API。                             |
| OSAL Wrapper                           | `04_platform/platform_os/os_wrapper/inc/` 与 `src/`                                                                  | 参数检查、统一类型和错误码、调用 Implementation；不放入 `07_os`。    |
| OSAL 具体 RTOS 适配实现                | `04_platform/platform_os/os_implementation/<实际RTOS>/inc/` 与 `src/`                                                | 统一接口到底层内核 API 的转换；不与原生内核 portable 端口混放。        |

用户指定的有 OS 架构布局如下。名称表示职责，具体文件数量、组件版本和内核子目录由实际工程决定：

```text
TARGET_ROOT/
├── 01_app/
│   └── app_init/
│       ├── 应用初始化代码
│       ├── platform_io_register/    平台外设注册
│       └── user_task_config/        任务及资源表、创建和句柄访问
├── 02_service/                     业务服务
├── 03_config/
│   ├── rtos_config.h               工程级资源参数（实际存在时）
│   └── cubemx/                     生成器配置
├── 04_platform/
│   └── platform_os/
│       ├── inc/                    OSAL 对上公开接口与 osal_config.h
│       ├── os_wrapper/
│       │   ├── inc/
│       │   └── src/
│       └── os_implementation/
│           └── <实际RTOS>/
│               ├── inc/
│               └── src/
├── 05_bsp/                         设备 Handler、Driver
├── 06_middlewares/                 非 OS 中间件
├── 07_os/                          OS 内核、原生端口、分配器及配置
├── 08_core/                        芯片启动、硬件初始化及中断入口
├── 09_drivers/                     CMSIS 芯片支持、HAL/LL
└── 10_toolchain/                   工程与构建配置
```

这是归类规则，不要求为未启用功能创建所有空目录。裸机工程不引入 `07_os` 和 `platform_os`；有 OS 的工程应归到以上对应位置，不能继续将内核作为普通 vendor 中间件归档。

按参考架构，上层通过以下接口方向使用 OS：

```text
App / Service
    -> platform_os/inc 中的公开 OSAL 接口
    -> platform_os/os_wrapper
    -> platform_os/os_implementation/<实际RTOS>
    -> 07_os 中的操作系统实现
```

`osal_config.h` 是 OSAL 选择及公共配置，`rtos_config.h` 是应用资源参数，`FreeRTOSConfig.h` 是 FreeRTOS 内核配置，三者不能互相替代。OSAL 架构是后续接入目标；若原代码仍直接使用 RTOS/CMSIS-RTOS API，目录迁移先保留其行为并说明尚未完成 OSAL 适配，不以搬文件冒充功能适配完成。

参考架构中的应用初始化代码负责创建资源和任务；内核源码本身不承载业务。若已有参考实现，应先确认原有实现与目标框架的职责及接口差异，不直接复制整套默认任务覆盖用户任务。

必须检查以下关联，而不是只把 RTOS 文件夹移动过去：

1. 构建实际选中的内核源文件、接口封装、portable 端口和分配器是否全部映射，并保留原文件排除规则。
2. 内核、端口、封装和工程配置的搜索目录是否全部更新；配置实际包含的其他头文件也应可解析。
3. main 中原有的内核初始化、对象/任务创建、调度器启动调用及顺序是否保留；不添加裸机轮询替代任务。
4. SVC、PendSV、SysTick 等与 RTOS 相关的处理函数、别名和向量绑定是否保持原工程设置。不能仅凭重名删除，也不能新增覆盖原有实现。
5. HAL 的时间基准来源、RTOS 的 tick 配置及中断优先级相关设置是否保持原样；迁移目录不重新设计时基或优先级。
6. 应用钩子、静态分配回调、堆相关符号、链接脚本及汇编依赖是否仍能解析。
7. 使用用户指定的标准 FreeRTOS 布局时，每个目标只启用一个实际适配的内核 portable 端口和一个所选 heap_x.c；原工程采用自定义分配器时保留其有效方案，不额外加入 heap_x.c。

对于其他 RTOS，用其实际组件和启动接口执行同样的依赖检查，不强行套用 FreeRTOS 文件名和函数名。

### 4.3 其他可选中间件

启用 USB、网络、文件系统、图形库、安全组件或其他软件包时，同样区分第三方实现、项目配置、生成的接口/适配代码和业务调用。按组件实际依赖更新引用，不仅迁移公共库目录而遗漏工程侧的配置或 Port 文件。

原工程没有某个组件时直接跳过该组件规则，不创建占位文件，也不把示例组件加入构建。

## 5. 移动文件并校验完整性

1. 在写入前一次性检查映射目标，发现同名冲突先处理用途和差异。
2. 按映射表移动文件，保持文件名、第三方层级及文件内容。
3. 对只移动的文件比较迁移前后哈希值；对需要修改的配置，先完成移动校验，再修改其引用。
4. 用本次扫描产生的映射表核对文件集合与目标是否存在。数量只对本次工程有效，不与教程、其他工程或上次生成的文件数比较；编译产物单独分类。
5. 全部文件确认到位后，仅清理已确认为空的旧目录。共享目录、未分类文件和用户新增内容必须保留。

建议按集合校验：本次识别的原文件集合应等于已映射迁移文件、明确原地保留文件及经用户授权另行处理文件的并集；各集合边界应清楚，不得遗漏。同一个共享文件可以被多个目标引用，不能按引用次数重复统计文件。

## 6. 必须检查和按需修改的配置

### 6.1 Keil：`.uvprojx`

检查全部 Target，不能只修改第一个目标。

| 配置项或内容                                | 需要处理的事项                                                                                          |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `FilePath`                                | 更新 C/C++、汇编、显式加入工程的头文件和库文件引用。                                                    |
| `Groups/Group/GroupName` 及组内 `Files` | 按目标 MOC 的分层名称重组工程树，文件归入其实际目标层，保留原有效构建设置。                             |
| `IncludePath`                             | 更新 C/C++、汇编及文件级覆盖设置中的搜索目录，补入已迁出的配置头文件目录。                              |
| 构建宏、文件排除和目标选项                  | 保留原值与作用范围，包括外设选择、RTOS、CPU/FPU、ABI 及编译器相关选项；只修正其中实际受影响的路径参数。 |
| 启动文件引用                                | 指向 `08_core/` 中适配当前芯片和工具链的启动文件。                                                    |
| 库引用及搜索路径                            | 同时检查显式库文件、链接器附加参数和库搜索目录。                                                        |
| 链接设置，例如 `ScatterFile`              | 实际存在自定义链接脚本时修正路径，保持内存地址、大小及链接方式原样。                                    |
| 构建前后命令                                | 检查脚本、输入固件、签名文件和输出目录引用，保持命令原含义。                                            |
| 输出及列表目录                              | 检查相对路径移动后的实际落点；按需调整，避免写入源码目录或覆盖其他目标产物。                            |

以下替换仅适用于工程从原 `MDK-ARM/` 移到 `10_toolchain/MDK-ARM/`，且文件按上节映射归档的情况：

| 原引用                           | 新引用                                          |
| -------------------------------- | ----------------------------------------------- |
| `../Core/`                     | `../../08_core/Core/`                         |
| `../Drivers/`                  | `../../09_drivers/`                           |
| `../Middlewares/<非OS组件>/`   | 依据其目标位置计算到 `06_middlewares/` 的引用 |
| `../Middlewares/<实际OS组件>/` | 依据其目标位置计算到 `07_os/` 的引用          |
| `startup_<芯片>.s`             | `../../08_core/startup_<芯片>.s`              |

不要将这些替换规则全局套用到所有文件。其他层级、绝对路径和未迁移的共享文件，应按实际映射重新计算。

若 HAL 配置头文件位于 `09_drivers/`，需要新增：

```text
../../09_drivers
```

其余常见头文件搜索目录示例：

```text
../../08_core/Core/Inc
../../09_drivers/<厂商HAL目录>/Inc
../../09_drivers/<厂商HAL目录>/Inc/Legacy
../../09_drivers/CMSIS/Device/<厂商>/<芯片系列>/Include
../../09_drivers/CMSIS/Include
../../06_middlewares/vendor/<实际组件>/Inc
```

这些是条件示例，只加入实际存在且原工程需要的目录。

有 OS 时还要按实际落点加入 `07_os` 中的内核头文件、所选 portable 头文件、内核配置及接口封装目录，以及已接入的 OSAL 公开接口、Wrapper 内部声明、Implementation 目录。工程级配置和资源表头文件的目录也要同步。不得只加 `07_os` 顶层而遗漏实际组件子目录。

#### 6.1.1 Manage Project Items 的 Group 与分层对齐

**验收要求：打开 Keil 后，Project 树和 Manage Project Items 中应能直接看到与目标分层一致的 Group 名称、顺序及文件归属。** 修改磁盘目录或 `FilePath` 不会代替 Group 重组，必须一并处理 `.uvprojx` 中的组结构。

默认使用目标 MOC 中实际存在的顶层目录名作为 Group 名，保持编号前缀和排序。以下名称来自分层规则，组件和文件仍按本次工程动态判断：

| Group 名称            | 应归入的工程项目                                                                                |
| --------------------- | ----------------------------------------------------------------------------------------------- |
| `01_app`            | 实际归档到 App 的应用控制、消息处理、业务任务等文件。                                           |
| `02_service`        | 实际归档到 Service 的业务服务文件。                                                             |
| `03_config`         | 工程中需要展示、且实际归档到配置层的头文件或配置项目。                                          |
| `04_platform`       | 实际归档到 Platform 的 Adapter、Wrapper、MCU/OS Port。                                          |
| `05_bsp`            | 实际归档到 BSP 的设备 Handler、Driver。                                                         |
| `06_middlewares`    | 实际归档到中间件层的算法、协议、文件系统等非 OS 组件。                                          |
| `07_os`（有 OS 时） | OS 内核、原生 portable 端口、分配器和随内核使用的接口封装等项目；不含 OSAL Wrapper 和业务任务。 |
| `08_core`           | 归档后的硬件入口、生成的外设初始化、中断、MSP、system 和启动汇编。                              |
| `09_drivers`        | CMSIS、厂商 HAL/LL，以及按 MOC 归入本层的配置头文件。                                           |
| `10_toolchain`      | 已作为工程项目展示的构建辅助文件、链接脚本等；不将构建产物加入编译。                            |

目标工程采用其他层名时使用其原名，不机械创建表中不存在的层。没有需展示文件的层可不创建空组；不要为了填满组而把未启用的代码或入口模板加入工程。

默认先按顶层分组。如果中间件、BSP 或平台模块较多，需要进一步区分，可使用带完整层级前缀的组名，例如：

```text
04_platform/platform_mcu
04_platform/platform_os/os_wrapper
04_platform/platform_os/os_implementation/<实际RTOS>
05_bsp/<实际设备>/driver
05_bsp/<实际设备>/handler
06_middlewares/vendor/<实际协议组件>
07_os/<实际RTOS组件>
09_drivers/CMSIS
09_drivers/<实际HAL目录>
```

这些是组名的命名约定，不表示磁盘目录会随改名自动变化，也不要求 IDE 将斜杠呈现为嵌套文件夹。同一工程选择统一粒度，按层级编号排序；旧的 `Application/User/Core`、不带层级前缀的 `Drivers/...`、`Middlewares/...` 等普通组应改为目标分层命名。

执行步骤：

1. 对每个 Target 建立“原文件项 → 迁移后路径 → 目标 Group”的对应关系，依据文件实际归属分类，不能只根据旧 GroupName 改名。
2. 一个旧组混有多个层的文件时拆分；多个旧组同属一个新层时可合并。同一源码在同一 Target 内不要因重组被重复加入。
3. 移动工程中的原文件项并保留其 `FileName`、`FileType`、`FilePath` 和文件级配置；更新后的 FilePath 应指向文件所在的新层。
4. 迁移前记录组级设置及其对文件的实际影响，包括宏、include、优化、汇编选项、排除构建和其他覆盖设置。拆组或并组时继承原有效设置；必要时转换为文件级设置，不能仅删除旧组配置。
5. 检查库文件顺序、自定义构建步骤等与组或项目顺序相关的设置。重排展示分组后仍须保持原链接依赖和有效构建行为。
6. 只把原本需要参与当前 Target 的源码加入其编译范围。头文件、配置或脚本如需展示，按合适类型添加；不把所有磁盘文件递归加入编译，不激活 RTOS 的全部 portable 端口或全部 heap 实现。
7. 根目录入口或未覆盖的文件单独按实际职责处理；只有当前镜像使用的入口参与构建，不为展示模板额外加入第二个 main。
8. 对 RTE/Pack 等工具管理节点先识别管理关系，通过工具支持的方式处理；不能强行改名或搬移而破坏组件管理。确有不可改名节点时单独说明，其余用户管理组仍需对齐。
9. 普通旧组文件迁出后再删除已无用途的空组。保留有效工程项目，不能通过删组丢弃文件引用。
10. 保存后重新读取全部 Target 的 GroupName、文件清单、文件路径及有效构建设置，确认层名、排序和归属一致；有 Keil 时重新加载项目检查树形展示。

重新使用 CubeMX 生成工程时，可能再次产生工具默认组名；归档流程应重新执行本节分组同步，不能只搬文件、改路径而遗漏工程树。

### 6.2 Keil：`.uvoptx`、调试和运行时配置

- `.uvoptx` 通常可随工程移动。仅修改受迁移影响的字段；Group 重组时，若文件保存了分组名称、GroupNumber、FileNumber、文件路径及显示状态，应与 .uvprojx 同步，保留其他调试设置。
- 检查调试初始化脚本、下载算法、外部工具、`DebugConfig/` 和 `RTE/` 的引用；区分工具链安装路径与工程内路径。
- `.uvguix.*` 等个人界面设置不作为固件源码；若原工程带有此类文件，应保留或按用户要求处理，不擅自删除。
- 保留调试器类型、下载参数和已有设备选择。目录迁移不需要重新选择芯片。

### 6.3 CubeMX：`.mxproject`

检查实际存在的段与字段，例如：

```text
[PreviousGenFiles]       HeaderFiles、SourceFiles、HeaderPath、SourcePath、各类 Size
[PreviousLibFiles]       LibFiles
[ThirdPartyIp...]        library、header
[PreviousUsedKeilFiles]  SourceFiles、HeaderPath
```

处理规则：

1. 分别确认各段路径原本的解析基准；不同字段可能采用不同基准，不应假定全部相对于 `.mxproject`。
2. 按迁移映射更新文件和目录引用。若原值是分号列表，逐项处理并保留列表语法。
3. HAL 配置头文件单独迁移时，同时更新文件引用和相关头文件目录记录。
4. 新增或减少编号项时同步 `Size` 等计数字段，保持编号与数量一致。
5. 历史记录引用了不存在的模板时，先确认工程实际采用的实现，只有确定对应关系后才修正；不得凭文件名猜测替代实现。
6. 不更改第三方包标识和组件版本，不因重排路径删除元数据。

### 6.4 CubeMX：配置与再次生成

**结论：仅搬动文件、修改 Keil 路径或 .mxproject，不会让 CubeMX 自动学会分层目录。未实现并验证回迁机制时，直接点击 Generate Code 不能保证输出仍落在整理后的目录，Keil 分组也可能被重新生成。**

`.ioc` 保留实际名称、芯片、引脚、时钟和外设参数。生成路径应在 CubeMX 的实际工程设置中确认，包括 Project Location、工具链目录和源码生成位置；具体字段随版本与工具链判断，不能只因 .ioc 放在 cubemx/ 就推断输出位置。

推荐区分两个根目录：

| 目录 | 用途 | 规则 |
| --- | --- | --- |
| GENERATION_ROOT | 独立 CubeMX 生成工作目录 | 按生成器支持的原始布局保存 Core、Drivers、Middlewares 和 IDE 工程等。 |
| TARGET_ROOT | 正式分层工程 | 保留 01_app 至 10_toolchain 的职责分层、有效工程设置及用户代码。 |

两个目录不能混淆，生成目录也不能选成正式分层工程中某个源码子目录。

#### 6.4.1 再生成前

1. 保存当前已确认可构建的工程、配置及用户代码，记录需要保留的 USER CODE 区域。
2. 在 GENERATION_ROOT 建立当前 .ioc 的生成副本；保留当前硬件和中间件选择，明确 CubeMX 实际输出位置。
3. 检查 CubeMX 的用户代码保留选项（界面通常称 Keep User Code when re-generating），并确认该版本的生成器识别原有标记。
4. 若正式工程的 main.c 或其他生成文件已经集成用户逻辑，按反向映射将这些文件复制到 GENERATION_ROOT 中生成器预期的位置，例如将目标的 08_core/Core/Src/main.c 复制到生成工作目录对应的 Core/Src/main.c。
5. 不只是 main.c：凡需要依靠 USER CODE 保留的生成文件，都应在生成器实际读取的位置有正确版本。不能只备份 main_frame.c，就认为已集成到硬件入口的内容会自动保留。
6. 不将 main_frame.c 复制为生成目录的 main.c。它是框架参考，不含完整硬件启动代码时不能充当生成基线。

**Keep User Code 只保留生成器实际处理文件中可识别的用户区域；它不会从已搬走的 main.c 或 main_frame.c 自动搜集应用逻辑，也不能保证保留写在用户区域之外的修改。**

#### 6.4.2 生成后检查与回迁

1. 在 GENERATION_ROOT 执行生成，确认本轮实际输出目录及文件；不要先假定输出符合上次映射。
2. 对生成结果重新扫描，识别新增、修改及不再生成的文件，更新本轮映射。文件数量和外设文件名都动态判断。
3. 以新生成的 main.c 为硬件代码基准，保留新的 HAL、时钟和外设初始化；核对并合入正式工程中已维护的 USER CODE 内容。
4. 将生成文件按本轮映射回迁到 TARGET_ROOT。main.c 仍归 08_core/Core/Src/main.c，不能因为同目录也有框架参考就覆盖错文件。
5. 重新检查全部目标的源码、include、库、启动文件和链接脚本引用。新增或移除外设/中间件后，文件集变化必须同步到正式构建。
6. 使用新生成工程作为硬件依赖参考，合并需要的增量配置；不能直接用它的 .uvprojx/.uvoptx 覆盖正式分层工程而丢失分组和原构建选项。
7. 按第 6.1.1 节同步 Manage Project Items 的 Group，文件按实际分层归组；同步 .uvoptx 中存在的分组/文件索引及相关缓存。
8. 检查入口、USER CODE 内容和实际构建清单，进行一次干净构建。有硬件时再按实际任务验证新外设功能。
9. 将本轮实际硬件配置同步回正式保存的 .ioc，保留适用于分层工程的相关引用；不把临时生成目录的绝对路径无意写入正式配置。
10. 不再生成的旧文件，只有确认属于生成文件、没有用户维护内容且不再被任何有效目标使用时，才按授权范围清理。用户文件和 main_frame.c 不因生成结果中不存在而被删除。

已有自动回迁脚本时，也应核对其是否同时处理：动态文件映射、用户区域合并、OS/非 OS 分流、工程内部引用和 Keil Group。未经验证，不能宣称生成后文件位置及分组会自动正确。

#### 6.4.3 本轮是否完成的判断

只有生成结果已回迁、用户代码保留、路径与 Group 对齐且验证通过后，才算分层工程更新完成。仅看到 CubeMX 成功生成 main.c，不代表正式分层工程已经更新。


### 6.5 其他构建工具与源码相对引用

工程实际存在时，再检查相应文件：

| 文件或配置                                        | 检查内容                                                               |
| ------------------------------------------------- | ---------------------------------------------------------------------- |
| CMake、Makefile、构建脚本                         | 源文件列表、include 目录、库、启动文件、链接脚本、工作目录和输出路径。 |
| GCC 链接脚本 `.ld`、Keil `.sct`、IAR `.icf` | 工程指向脚本的路径，以及脚本内部对其他文件的引用；保留原内存布局。     |
| IAR 等 IDE 工程                                   | 按该 IDE 的宏和路径基准更新实际字段。                                  |
| `.vscode/`                                      | 存在时检查 IntelliSense、任务、调试、工作目录和程序文件路径。          |
| C/H/汇编源文件                                    | 检查 `../` 等显式相对 include、汇编 include、二进制资源引用。        |

优先修正构建系统的搜索路径。确需修改源码引用时，只修改失效路径，保留业务和寄存器操作逻辑。

## 7. 保留生成 main.c，并接入 main_frame.c

### 7.1 两份文件的职责

| 文件 | 职责 | 是否参与编译 |
| --- | --- | --- |
| CubeMX 生成并回迁到 08_core/Core/Src/main.c 的文件 | 正式硬件入口，保留 main()、HAL_Init、系统时钟、实际外设初始化以及适用时的 OS 启动流程。 | 作为所属固件镜像的实际入口参与编译。 |
| 08_core/Core/Src/main_frame.c（原框架 main.c） | 框架接入参考，提供应用头文件、初始化、裸机轮询或任务接入逻辑。 | 仍含 main() 时不加入编译，或在所属目标明确排除构建；仅改文件名不会消除 main() 定义。 |

**保留 CubeMX 的 main.c，在它已有的 main() 内接入框架逻辑。不要用 main_frame.c 整体覆盖生成文件，也不要把两个 main() 同时编译。**

用户将框架文件改名为 main_frame.c 时，保留其中内容即可；如果工程曾引用旧框架文件，按新用途同步引用或排除状态。保持每个独立固件镜像只有一个有效 main()。

框架参考文件现放在 `08_core/Core/Src/main_frame.c`；**不要把 CubeMX 生成并用于构建的 08_core/Core/Src/main.c 改名为 main_frame.c**。生成文件继续保留生成器预期的名称及 USER CODE 标记。

### 7.2 USER CODE 区域的合入规则

用户要求接入框架时，先阅读生成 main.c 与 main_frame.c，提取必要逻辑，去重后合入相应用户区域。区域名称以实际生成文件为准，下表是常见位置：

| 常见区域 | 可以接入的内容 | 注意事项 |
| --- | --- | --- |
| USER CODE BEGIN Includes | 应用控制、消息队列、Service、Wrapper 等实际需要的头文件。 | 同步 Keil 搜索路径，不复制无关 include。 |
| PV / PTD / PD / PM / PFP 等用户区域 | 实际需要的变量、类型、宏和函数声明。 | 保留作用域，避免与新生成声明冲突。 |
| USER CODE BEGIN 0 或 4 | 必要的用户辅助函数。 | 不在生成 main.c 复制第二个 main()；可复用模块的实现尽量保留在其职责层。 |
| USER CODE BEGIN 2 或等效的硬件初始化后区域 | 框架初始化、平台注册、设备/应用初始化。 | 依据真实依赖确定顺序，检查原初始化错误处理；不要提前访问尚未初始化的外设，也不要重复初始化硬件。 |
| 裸机 while 循环内部的 USER CODE BEGIN 3 等区域 | 框架要求的消息轮询或应用周期调用。 | 必须在循环体内，不改写生成器维护的循环结构；只保留一份相同轮询逻辑。 |
| RTOS 任务或对象初始化文件中的用户区域 | 任务业务、资源创建及适配调用。 | 按 OS 架构接入，保留调度器启动顺序，不用 main 中的裸机轮询替代任务。 |

只把实际已有的框架能力接入，不凭模板创建不存在的业务 API。原有队列初始化、应用控制初始化、消息处理等需要哪些对象和错误处理，应以实际实现为准。

裸机流程的职责示意：

```text
CubeMX 维护的 main()
    -> 原 HAL / 系统时钟 / 实际外设初始化
    -> USER CODE：按依赖初始化框架与应用
    -> 原 while (1)
        -> USER CODE：应用消息轮询或周期处理
```

有 OS 时，保留原内核初始化、对象/任务创建和调度器启动关系，将业务执行放在对应任务中。参考 OSAL 框架未完成适配时，明确剩余工作，不能为使模板看似接入就改写成裸机。

### 7.3 再次生成时如何保留接入内容

- 两个架构的 main_frame.c 均放在 `08_core/Core/Src/`，供使用时手动合并；合并完成后手动删除参考文件。正式运行的应用接入内容以已集成的生成 main.c 及应用模块为准。
- 只改名 main_frame.c，不能保护另一份 main.c 中的应用修改。生成前应把已集成的生成文件按第 6.4 节同步到生成工作目录，或在生成后可靠合并用户区域。
- 保留所有 USER CODE BEGIN/END 标记，不能将业务修改放在生成器会重建的区域后假定其会保留。
- 回迁时采用“新生成的硬件代码 + 保留的用户逻辑”，不拿旧 main.c 整体覆盖新文件，否则可能丢失本轮新增外设及启动代码。
- 每次合入应可重复执行而不重复添加 include、初始化或轮询语句；再次核对 main、ISR、HAL 回调和 RTOS 异常入口。
- 用构建检查实际编译的 main.c 是否就是最新回迁文件，避免 CubeMX 生成成功但 Keil 仍编译另一份旧入口。

这些用途说明写在独立教程或交付说明中，**不要写入或修改 MOC**。


## 8. 验收标准

- [ ] 所有 MOC 内容与迁移前一致，没有替换示例文件名或新增迁移章节。
- [ ] 映射中的原文件均已到位，无覆盖、遗漏及不必要的重复副本。
- [ ] 文件完整性按本次扫描集合验收，不要求固定文件数、外设数或 include 目录数。
- [ ] 只移动文件的内容校验通过，配置修改能够解释到具体路径字段。
- [ ] 每个构建目标的源文件、库、启动文件和链接脚本引用均能解析。
- [ ] 每个 Keil Target 的普通 Group 按目标分层命名和排序，组内文件与实际迁移层一致，旧默认组已按需拆分或合并。

- [ ] 所有需要的头文件搜索目录均存在，HAL 配置头文件可被正确找到。
- [ ] XML 等配置格式有效，编号列表与计数一致。
- [ ] 每个独立链接镜像的 main、中断入口和 system 实现没有意外重复或缺失，合法多目标和多核结构保持原样。
- [ ] 实际使用的外设及可选中间件依赖完整；没有增加示例组件或丢失生成的适配代码。
- [ ] 使用 RTOS 时，内核、封装、端口、分配器、配置、任务创建、时基及异常入口关系保持原样且路径可解析。
- [ ] 有 OS 时，内核归 `07_os`，OSAL 归 `04_platform/platform_os`，业务任务归 App，资源参数按职责归 Config；Keil Group 与这些位置一致。

- [ ] 用户的已有配置、硬件参数、内存布局、业务逻辑和第三方许可证得到保留。
- [ ] 检索旧目录引用并逐条确认；共享依赖和无效历史项不能用全局替换处理。
- [ ] 有可用工具链时执行一次干净构建，防止旧目标文件掩盖路径错误。
- [ ] 无工具链时明确只完成静态路径和配置检查；不得声称编译、下载或硬件验证通过。
- [ ] CubeMX 再生成策略明确，不把元数据修正等同于自动分层生成支持。
- [ ] main_frame.c 保留作框架参考；若仍定义 main()，已从实际编译中排除，生成的 main.c 是对应镜像的唯一入口。
- [ ] 用户要求框架接入时，必要逻辑已合入生成 main.c/RTOS 文件的 USER CODE 区域，且未覆盖硬件初始化或重复添加调用。
- [ ] 再生成的文件已按本轮映射回迁，新增硬件代码和已集成用户代码同时保留。
- [ ] CubeMX 再生成后重新核对 Keil 分组及 .uvoptx 索引，未直接用默认生成工程覆盖分层工程。
