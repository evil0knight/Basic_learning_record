## FPU 是什么

FPU（Floating-Point Unit）是**浮点运算单元**。Cortex-M4 的 FPU 是可选部件，带 FPU 的实现通常称为 Cortex-M4F，必须确认具体芯片支持。

浮点数的表示与精度见 [存储浮点数](../../书中自有黄金屋/计算机组成原理/存储浮点数.md)；加减乘除的原理、例子及阶码偏置推导见其中的 [浮点数的加减乘除](../../书中自有黄金屋/计算机组成原理/存储浮点数.md#浮点数的加减乘除)。

## 软件浮点与 FPU 硬件浮点

| 实现         | 执行过程                                                         | 使用的资源                                           |
| ------------ | ---------------------------------------------------------------- | ---------------------------------------------------- |
| 软件浮点     | 编译器调用运行库，用整数指令拆字段、移位、加减乘除、规格化和舍入 | 通用寄存器、整数运算单元、多条指令                   |
| FPU 硬件浮点 | 编译器生成浮点指令，由专用电路完成上述步骤                       | 浮点寄存器、对阶移位电路、运算电路、规格化及舍入电路 |

两者都要遵循所选格式及运算规则。FPU 主要加速计算，**不会消除有限精度误差**；具体结果还受舍入模式、是否融合运算、是否冲零等配置影响。

Cortex-M4F 常见的 FPv4-SP-D16 支持单精度加减乘除、平方根、比较、转换及乘加等指令，例如 `VADD.F32`、`VMUL.F32`、`VDIV.F32`、`VSQRT.F32`。不同指令耗时不同，不能理解为“所有浮点运算都只需一个周期”。

数据流可以理解为：

```text
内存中的 float
    ↓ VLDR / 数据搬运
S 浮点寄存器 → FPU 运算 → S 浮点寄存器
                              ↓ VSTR / 数据搬运
                           写回内存
```

`VMOV` 搬运位模式，数值类型转换使用 `VCVT` 等指令；把整数位模式搬到浮点寄存器，不等于把该整数转换为浮点值。

`sin`、`cos`、`log` 等不是 M4F 的单条硬件指令，仍由数学库算法实现；单精度库可以利用 FPU 加速其中的基本运算。

## 浮点寄存器组与控制位

### 数据与状态寄存器

| 寄存器       | 用途                                                      | 保存责任                                                                       |
| ------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `S0–S15`  | 16 个 32 位浮点寄存器；硬浮点调用约定下也用于传参和返回值 | 异常机制自动保存的浮点数据部分                                                 |
| `S16–S31` | 另外 16 个 32 位浮点寄存器                                | 异常硬件不自动保存；按调用约定由编译器或汇编代码保护，任务切换由 RTOS 端口处理 |
| `FPSCR`    | 浮点比较标志、舍入模式、累计异常标志、FZ/DN 等控制        | 与 `S0–S15` 一起自动保存                                                    |
| `FPDSCR`   | 新浮点上下文所用的默认浮点控制设置                        | 不能代替当前上下文的 `FPSCR`                                                 |

**数据存在哪：**`S0–S31` 共 32 个寄存器，每个 32 位，共 128 字节。把相邻两个合起来看，就是一个 64 位的 `D` 寄存器：`D0 = S0/S1`、`D1 = S2/S3`，一直到 `D15 = S30/S31`。两套名字指向同一块存储，修改其中一个，另一种叫法看到的内容也会改变。型号中的 `D16` 就指这 16 个 `D` 寄存器；**能存 64 位数据，不代表 M4F 能做双精度运算**。

**为什么要保存现场**：任务和中断共用这组寄存器。任务算到一半，中断也要用 FPU，就需要先把任务仍需保留的浮点状态存到栈里，返回时恢复，任务才能接着算。

**运算规则由谁管：**`FPSCR` 保存浮点控制和状态。其中 `FZ` 决定是否把非规格化的极小数按零处理，`DN` 决定是否使用统一的默认 NaN。发生除零、溢出等情况时，FPU 可在其中留下异常标志；**留下标志不等于触发中断**。

### 控制自动保存的关键位

| 寄存器/字段         | 含义                                                           |
| ------------------- | -------------------------------------------------------------- |
| `CPACR.CP10/CP11` | FPU 访问权限；未使能时执行浮点指令可产生 NOCP UsageFault       |
| `CONTROL.FPCA`    | 当前执行上下文是否具有活动的浮点状态；不等于“此刻正在算浮点” |
| `FPCCR.ASPEN`     | 自动维护浮点上下文状态，执行浮点指令时自动激活上下文           |
| `FPCCR.LSPEN`     | 在自动保存机制下启用惰性保存                                   |
| `FPCCR.LSPACT`    | 存在尚未完成的惰性浮点保存                                     |
| `FPCAR`           | 指向待保存浮点状态的预留栈区                                   |
| `EXC_RETURN[4]`   | 本次异常返回所对应的帧类型：`1` 为基本帧，`0` 为扩展浮点帧 |

“有浮点上下文”通常指此前执行过浮点指令、浮点状态仍处于活动状态；即使下一行 C 代码全是整数，也不代表 `FPCA` 已清零。编译器、库函数也可能使用浮点寄存器，不能只看源码中有没有 `float`。

## 异常栈帧与惰性压栈

### 基本帧和扩展帧

普通异常入口硬件保存 `R0–R3、R12、LR、PC、xPSR`，共 **8 个字，即 32 字节**。

有活动浮点上下文时，还需保护 `S0–S15、FPSCR`，并留一个保留字，共 **18 个字，即 72 字节**。扩展帧合计 **104 字节**，不含可能的对齐填充、编译器保存的寄存器及局部变量。

这些内容不包括 `S16–S31`。完整任务切换还需要软件处理高半组浮点寄存器以及其他任务状态。

被打断线程若使用 PSP，其异常帧就保存在 PSP 对应的任务栈；随后 ISR 使用 MSP。若被打断线程使用 MSP，帧就在 MSP；嵌套中断保存 ISR 现场时也使用 MSP。不是“只要进入中断，所有现场就都压到 MSP”。

### 先留座，真正要用时再搬

以下各场景默认 **FPU 已开启，`ASPEN=1、LSPEN=1`**，ISR 遵守调用约定，并暂不考虑 RTOS 切换和尾链。

1. 有活动浮点上下文的代码被打断，硬件保存基本帧，并为浮点部分**预留栈空间**。
2. 此时原浮点内容仍在 FPU 寄存器中，`LSPACT=1`，`FPCAR` 记录预留区；扩展帧对应的 `EXC_RETURN[4]=0`，但预留区尚未装入有效浮点现场。
3. 若 ISR 始终不用 FPU，返回时取消这次预留即可，不必真正写入或读回这些浮点寄存器。
4. 若 ISR 执行需要使用 FPU 的指令，硬件先完成待处理的浮点保存，再允许 ISR 使用寄存器；保存完成后，这次待处理状态解除。

**预留空间也会消耗栈容量**。惰性保存节约的是不必要的内存传输及其时间，不是把扩展帧所需空间省掉。

若 `ASPEN=1、LSPEN=0`，活动浮点上下文在异常入口就立即保存，入口开销更大、时间分布更直接。`ASPEN=0` 时必须另行设计上下文管理，不能照搬下文的自动处理过程。

## 单层中断：按任务与 ISR 是否使用浮点区分

下面的“任务无”指进入中断前没有活动浮点上下文；“ISR 有”指 ISR 实际执行了浮点指令。

| 被打断的任务 | ISR | 异常入口                         | ISR 执行与返回                                                                           |
| ------------ | --- | -------------------------------- | ---------------------------------------------------------------------------------------- |
| 无           | 无  | 只压基本帧                       | 不涉及浮点保存和恢复                                                                     |
| 无           | 有  | 只压基本帧，无任务浮点区需要预留 | ISR 可建立自己的浮点上下文；返回任务时按基本帧恢复，不必保存一个本来不存在的任务浮点现场 |
| 有           | 无  | 基本帧写入，浮点区预留           | 原任务浮点值留在寄存器；返回时释放预留区，不发生浮点数据保存/恢复                        |
| 有           | 有  | 基本帧写入，浮点区预留           | ISR 首次使用 FPU 前，把任务低半组浮点现场写入预留区；异常返回时从扩展帧恢复任务现场      |

最后一种情况的时序：

```text
任务 T 使用 FPU
  → ISR A 进入：预留 T 的浮点区，T 的浮点值暂留寄存器
  → A 首次使用 FPU：先保存 T 的 S0–S15/FPSCR，再计算
  → A 返回：恢复 T 的浮点现场，T 继续运行
```

表中的自动保存只针对低半组。若 ISR 使用 `S16–S31`，其编译器生成的入口/出口代码或手写汇编还必须保护它们，不能等待异常硬件代劳。

## 嵌套中断：任务 T → ISR A → 更高优先级 ISR B

以下分别说明中断处理程序 A、B 的浮点使用情况。嵌套时 B 对应的异常帧保护的是 **A 被打断时的状态**，但尚未完成的惰性保存可能属于更早的 T。

### A 不用浮点，B 使用浮点

**T 无浮点上下文：**

1. T → A 只压基本帧；A → B 也只压基本帧。
2. B 使用 FPU 时建立自己的上下文，没有 T/A 的浮点现场需要先保存。
3. B 返回 A、A 返回 T 均按各自基本帧恢复；浮点寄存器残留值不代表返回的代码拥有活动浮点上下文。

**T 有浮点上下文：**

1. T → A：预留 T 的浮点区，任务浮点值仍在寄存器中。
2. A 没用 FPU，因此 A 本身没有活动浮点上下文；A → B 为 A 压基本帧，不为 A 再建一份浮点扩展帧。
3. B 首次使用 FPU，触发的待保存状态属于 **T**：硬件把 T 的低半组浮点状态写入先前预留的 T 栈区，然后 B 才使用 FPU。
4. B 返回 A 时不恢复一份不存在的 A 浮点现场；A 返回 T 时，才从 T 的扩展帧恢复任务浮点状态。

因此，**谁触发实际保存，不一定就是谁的栈接收这份保存**。若 T 用 PSP，B 触发的这次保存仍写到 T 的 PSP 栈区，而非 B 当前使用的 MSP 栈区。

### A、B 都使用浮点

先假设 **A 已实际执行浮点指令，随后被 B 打断**：

1. 若 T 有浮点上下文，A 首次使用 FPU 时已经把 T 的待保存状态写入任务栈；若 T 没有，就不存在这一步。
2. A → B：A 有活动浮点上下文，硬件在 MSP 栈上为 A 预留浮点区。
3. B 首次使用 FPU：先把 A 的低半组浮点现场写入 A 的预留区，再执行 B 的运算。
4. B 返回：恢复 A 的浮点现场，A 继续计算。
5. A 返回：若 T 有浮点上下文，恢复 T 的扩展帧；否则按 T 的基本帧返回。

```text
T 的浮点现场 → T 的栈帧（T 有活动浮点状态时）
A 的浮点现场 → MSP 上 A 被打断形成的栈帧
B 运行时      → 使用当前唯一的一组 FPU 寄存器
```

如果 B 抢占时，**A 尚未执行第一条浮点指令**，即使 A 后面会算浮点，当时也应按上一节“A 不用浮点”的状态处理；恢复 A 后，它首次用 FPU 时再根据那时的上下文状态处理。应按实际执行时刻判断，不能只按 ISR 函数里是否写了浮点代码判断。

### A 使用浮点，B 不使用浮点

A → B 时为 A 预留浮点区。B 不触碰 FPU，A 的浮点寄存器保持原值；B 返回时释放预留区即可，A 继续运行。B 若只执行整数逻辑，就避免了 A 浮点现场的实际传输。

更多层嵌套按同样规则处理：每层异常帧描述自己的返回对象，不能把所有层的浮点保存当作同一个全局栈帧；每层都要计入最坏栈容量。

## 压栈过程中或浮点指令执行中被中断

### 惰性压栈过程中又来高优先级中断

要区分两个时刻：

- **仍只是预留，尚未开始实际保存**：可以直接进入更高优先级中断；它若使用 FPU，就可能触发原先待处理的保存，见“A 不用浮点，B 使用浮点”。
- **已经在实际保存浮点状态**：惰性状态保存支持可中断处理，硬件维护保存进度及正确的异常状态，随后完成相应保存。不能将整个 72 字节传输理解为关中断的不可抢占操作，也不能理解为随意留下半份现场供上层覆盖。

软件不应在这种过程中擅自改写 `FPCAR`、清除状态或回收原栈区。ISR 的第一条浮点指令可能附带一次延后的保存开销，故惰性保存降低了常见入口开销，却会使首次使用 FPU 的延迟发生变化。

### 执行浮点指令时来了中断

“浮点指令被中断”是 **NVIC 异常抢占正常浮点代码**，不是浮点数算错自动触发中断。

- 对单个算术结果，异常处理程序看到的是架构允许的完整状态，不会看到“一个 S 寄存器只更新一半”的结果。
- M4F 的浮点除法、平方根等较长运算可在异常处理机制下被放弃并在返回后重新执行，不能一概认为必须等待整条长指令计算完才响应中断。
- 多寄存器传送等指令另有可继续/重启规则，不能把所有 FPU 指令都当成相同的单周期、不可中断操作。
- 随后的浮点上下文保护仍按上述规则处理：有活动状态就需要保留；ISR 是否真正使用 FPU，决定预留区是否需要实际写入。

估算实时性时，应同时考虑异常入口、可能延后的浮点保存、当前指令的可中断特性，以及嵌套深度，不能仅按 C 源码中的一行计算耗时。

## 使用：单精度函数与 Target 的 Use FPU

### 工程配置

1. 确认 MCU 实际带单精度 FPU，并在工程中选择正确器件。
2. Keil µVision 在 **Options for Target → Target → Floating Point Hardware / Use FPU** 处选择与芯片匹配的单精度 FPU；具体字段名随工具链版本变化，不能为无 FPU 的芯片强行勾选。
3. 确认启动代码在执行任何浮点指令前已开放 `CPACR` 的 CP10/CP11 访问权限；CMSIS 常根据 `__FPU_PRESENT`、`__FPU_USED` 在 `SystemInit()` 中处理。配置及屏障片段见 [剩余寄存器](剩余寄存器.md#fpu)。
4. 确认各目标文件和库的浮点 ABI 一致；选择正确的 RTOS FPU 端口，并为任务栈、中断栈预留浮点上下文空间。
5. 查看反汇编，确认预期单精度运算生成了 `VADD.F32`、`VMUL.F32` 等指令，而非全部调用软件浮点函数。

GCC 常用 `-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16`，再按工程和库选择 `-mfloat-abi`：

| 选项       | 运算及调用约定                                   |
| ---------- | ------------------------------------------------ |
| `soft`   | 使用软件浮点及基础调用约定                       |
| `softfp` | 可生成硬件浮点指令，但用基础调用约定传递参数     |
| `hard`   | 可生成硬件浮点指令，并用浮点调用约定传递相应参数 |

`softfp` 不等于“不用 FPU”；`hard` 与基础浮点参数调用约定不能随意混链。Target 的 FPU 选项决定编译方式，`CPACR` 决定运行时是否允许访问，二者都需正确。

### 数学函数使用单精度版本

| 单精度写法                               | 容易引入双精度的写法                             |
| ---------------------------------------- | ------------------------------------------------ |
| `float x = 0.1f;`                      | `0.1` 默认是 `double`                        |
| `x * 2.0f`                             | `x * 2.0` 使表达式提升到 `double`            |
| `sinf(x)`、`cosf(x)`                 | `sin(x)`、`cos(x)` 参数和返回值是 `double` |
| `sqrtf(x)`、`fabsf(x)`               | `sqrt(x)`、`fabs(x)`                         |
| `logf(x)`、`expf(x)`、`powf(x, y)` | `log(x)`、`exp(x)`、`pow(x, y)`            |

使用这些函数需包含 `<math.h>`，并按工具链配置数学库。给 `float` 变量赋值并不会让右侧的 `double` 运算自动变成单精度；M4F 没有双精度算术硬件，双精度计算通常需软件支持。

`printf("%f", x)` 是另一种情况：可变参数规则会将 `float` 提升为 `double`；不能靠改写成 `%lf` 或给数值加 `f` 来避免。打印还涉及库函数执行时间和栈开销，不适合放进要求低延迟的 ISR。

### RTOS 与中断中的保护边界

- 普通异常自动处理 `S0–S15/FPSCR`；`S16–S31` 的保存不能遗漏，遵守 ABI 的 ISR 编译器会保护被它使用的高半组寄存器。
- RTOS 切换任务要保存该任务后续仍需使用的全部浮点状态，通常由 FPU 端口结合硬件扩展帧和软件保存高半组实现；单靠打开惰性压栈不足以实现任务隔离。
- 手写汇编 ISR、裸函数或自行修改异常返回流程时，必须自行满足相应保存约定；不要把普通函数调用约定误当作完整任务切换规则。
- 最坏栈容量要计入每层可能的扩展帧、软件保存区和 ISR/数学库局部栈；“多数中断不用 FPU”不代表可以不预留容量。
